# MAEK 구조 검토 및 팀 인수인계

- 검토일: 2026-11-06
- 대상: `nalziori/MAEK`, `main`, 커밋 `0bbf4ff351341a3998a4f7dfb65363b35beaa681`
- 목적: 현재 구조에서 실행과 결과 신뢰성을 해치는 문제를 확인하고 팀원이 이어서 수정할 수 있도록 전달한다.
- 방법: `dispatching-parallel-agents`로 구조·평가·실행 경로를 병렬 검토하고 `ponytail-audit` 기준으로 재현 근거를 검토했다.
- 변경 범위: 이 보고서 작성과 검증 환경 구성. 제품 코드 수정·커밋·푸시는 하지 않았다. 기존 Graphify 설정 파일은 이번 검토 전부터 미추적 상태였다.

## 판단과 전제

이 저장소는 제철소 배관망과 결함, 카메라·열화상·초음파 데이터를 합성하고 검사 방식별 성능·비용을 비교하는 Python CLI 시뮬레이터다. 연구·해커톤에서 한 사용자가 실행하는 규모를 전제로 검토했다.

현재 규모에서 CLI와 도메인 모듈을 나눈 구조는 유지할 수 있다. 먼저 고칠 부분은 대규모 아키텍처 개편보다 **실행 환경의 경계, 데이터셋 출력의 일관성, 평가 지표와 재현 정보의 정확성**이다. 아래 7건은 코드 또는 통제된 입력으로 확인했다. 기본 데이터 전체에 대한 수치 변화량은 측정하지 않았다.

## 현재 구조

```text
python -m maek
  └─ maek/__main__.py → cli.py
       ├─ params.py: 기본 YAML → 시나리오 병합 → --set → 검증
       ├─ network.py: 배관 구간·특징·결함 정답 생성
       ├─ camera/: 촬영 작업 → 합성 RGB·클래스 마스크 → HSV 분할
       ├─ ut.py / pit.py: 초음파 신호·두께·균열·피팅 분석
       ├─ heat.py / thermal.py / thermal_render.py / pec.py: 보조 센서 모델
       ├─ energy.py / eva.py / pod.py: 손실·극값·검출 확률 계산
       ├─ strategy.py: 사람·드론·드론+AI 비교
       ├─ evaluate.py: 성능 집계와 결과 표
       └─ onboard.py: 별도 워커를 실행해 CPU·메모리 측정

scripts/produce_data.py: 위 기능을 조합해 릴리스 데이터 생성
scripts/train_yolo_seg.py: 별도 YOLO 학습·평가·변환·벤치마크
config/: 기본 파라미터와 steam 시나리오
tests/: 기능별 테스트 / .github/workflows/ci.yml: Ubuntu·Python 3.12
```

기본 영상 분석은 HSV 규칙 기반이다. YOLO 모델은 별도 스크립트에서 다룬다. 전략 비교의 검출 확률·단가 가정과 실제 학습 모델의 성능을 같은 근거로 취급하면 안 된다. 실제 데이터·장비 검증 부재와 가정값은 README에도 명시돼 있어, 그 자체를 새 결함으로 분류하지 않았다.

## 우선순위

P1은 현재 Windows 실행 또는 성능 수치 공유 전에 먼저 해결할 항목, P2는 해당 실행·배포 경로를 사용하기 전에 해결할 항목이다. 담당은 확정된 사람 이름이 아닌 역할 제안이다.

| 번호 | 우선순위 | 문제 | 담당 역할 | 완료 기준 |
|---|---|---|---|---|
| 1 | P1 | Windows에서 onboard import 및 전체 테스트 수집 실패 | 실행·CI | 지원 플랫폼 정책 확정, 지원 환경의 전체 테스트 수집 성공 |
| 2 | P1 | 카메라 결함별 hit에 이웃 결함 픽셀이 섞임 | 영상·평가 | 이웃만 검출한 경우 원래 결함은 miss |
| 3 | P2 | 재생성한 데이터에 이전 출력이 남고 benchmark에 섞임 | 데이터·학습 도구 | 현재 manifest와 benchmark 입력 집합 일치 |
| 4 | P2 | 릴리스 카드·manifest에 실제 생성 설정이 보존되지 않음 | 데이터·재현성 | 당시 유효 설정과 전체 실행 인자로 재생성 가능 |
| 5 | P2 | 외부 CWD에서 onboard의 상대 출력 경로가 워커와 불일치 | 실행·CLI | 외부 CWD·상대 --out으로도 같은 설정 사용 |
| 6 | P2 | 두께 MAE가 추정 실패를 제외하지만 이름에 드러나지 않음 | 초음파·평가 | 유효 표본 MAE와 실패율을 함께 출력 |
| 7 | P2 | 전부 검출된 표본에서 a90 상한을 단정 | 평가·결과 문서 | 관측 사실과 추정 불가 상태를 구분 |

## 확인된 문제

### 1. Windows에서 onboard를 가져올 수 없다

- **근거:** [maek/onboard.py](../../maek/onboard.py) 11행의 최상위 `import resource`, 56행의 `_rss_mb`; [tests/test_eval_onboard.py](../../tests/test_eval_onboard.py) 6행. CI는 Ubuntu만 실행한다.
- **문제:** `resource`는 현재 Windows Python에 없다. 따라서 `onboard` 명령뿐 아니라 해당 모듈을 가져오는 테스트 파일의 수집도 중단된다.
- **실제 재현:** `.venv/Scripts/python.exe -c "import maek.onboard"` 및 `.venv/Scripts/python.exe -m pytest -q --tb=short`에서 `ModuleNotFoundError: No module named 'resource'`를 확인했다. 전체 테스트는 실행 전에 수집 단계에서 멈췄다.
- **최소 수정:** Windows 지원이 필요하면 RSS 측정의 플랫폼 분기를 두고, 미지원 측정값은 명시적으로 표시하되 나머지 기능과 테스트를 가져올 수 있게 한다. Linux 전용이라면 지원 환경과 실행 경로를 문서에 명시한다. Linux의 KiB 단위를 다른 플랫폼에 그대로 적용하지 않는다.
- **미수정 영향:** Windows 팀원은 탑재 측정과 전체 테스트를 진행할 수 없다. Linux에서도 실패한다고 주장하는 항목은 아니다.
- **회귀 검증:** 지원하는 운영체제에서 import·CLI·테스트 수집을 확인한다. 메모리 지표를 생략하면 0MB나 통과로 표시하지 않는다.

### 2. 카메라의 개별 결함 검출률에 이웃 결함이 영향을 준다

- **근거:** [maek/evaluate.py](../../maek/evaluate.py) 87~107행, [maek/camera/composite2d.py](../../maek/camera/composite2d.py) 180~196행.
- **문제:** 결함별 hit 계산이 해당 결함의 정답 픽셀이 아니라 `원형 탐색창 & 전체 부식 클래스 마스크`를 사용한다. 같은 클래스의 이웃 결함이 창 안에 있으면 원래 결함을 놓쳐도 hit가 된다.
- **실제 재현:** 64×64 입력, `width_frac=.6`, `tilt_deg=0`에서 A 중심 `(20,20)`, `w=h=.4`, B 중심 `(33,21)`, `w=h=.125`로 구성했다. A의 정답 영역 `mask[18:22,18:22]` 16픽셀을 모두 놓치고, B의 정답 영역 `[17:25,29:37]` 64픽셀만 예측하도록 `segment_rust` 반환을 통제했다. 실제 `eval_camera_image`는 A와 B 모두 `hit=True`를 반환했다. 전체 렌더링 결과의 오염 비율을 측정한 것은 아니다.
- **최소 수정:** 렌더러가 클래스 마스크와 별도로 결함별 instance ID 마스크를 반환하게 하고, 결함별 가시 픽셀에서 hit를 집계한다. 열화상 평가의 `ids == k + 1` 경로가 참고 구현이다. 기존 `render_job` 호출자와 반환 계약, 테스트를 함께 맞춰야 한다.
- **미수정 영향:** 결함 크기와 검출 여부가 잘못 연결돼 결함별 hit율·POD 추정값이 달라질 수 있다. 이미지 전체 IoU가 같은 이유로 잘못됐다고 단정하지 않는다.
- **회귀 검증:** 겹치지 않는 두 결함 중 한 개만 예측한 사례에서 `miss/hit`를 구분한다. 겹침·가림이 있는 경우 가시 정답 픽셀 기준도 고정한다.

### 3. 같은 폴더에 재생성하면 이전 이미지가 벤치마크에 섞인다

- **근거:** [maek/camera/composite2d.py](../../maek/camera/composite2d.py) 400행 이후, [maek/thermal_render.py](../../maek/thermal_render.py) 558행 이후, [scripts/train_yolo_seg.py](../../scripts/train_yolo_seg.py) 48~55행과 83행 이후.
- **문제:** 생성기는 현재 파일을 쓰지만 더 이상 사용하지 않는 이전 파일은 남긴다. 벤치마크의 `find_images`는 현재 train/val 목록 대신 `images/*`를 열거한다.
- **실제 재현:** 임시 디렉터리에 64px 이미지 2개를 생성하고 같은 경로에 1개로 줄여 다시 생성했다. 현재 train+val은 `J000000.jpg` 1개지만 benchmark는 `J000000.jpg`, `J000001.jpg` 2개를 읽었다. images/masks/labels의 파일 수도 각각 2개였다.
- **최소 수정:** 데이터셋 출력이 이미 있으면 명확히 중단하고 새 경로를 요구하는 방식부터 적용한다. 벤치마크는 현재 데이터셋 목록에 포함된 파일만 읽도록 한다. 기존 사용자의 출력 전체를 임의로 삭제하는 방식은 피한다.
- **미수정 영향:** 릴리스 폴더와 속도 측정에 이전 조건의 이미지가 섞인다. YOLO 학습은 train/val 목록을 사용하므로 같은 방식으로 학습이 오염됐다고 단정하지 않는다.
- **회귀 검증:** 2→1개 재생성, PNG→JPEG 전환, 현재 목록과 실제 측정 입력의 집합 일치를 확인한다.

### 4. 데이터 카드가 실제 설정을 기록하지 않는다

- **근거:** [scripts/produce_data.py](../../scripts/produce_data.py) 81~89행의 설정 로드, 132행의 manifest 저장, 138행 이후 `_card`. 144행의 설정명과 150행의 100km 문구가 고정돼 있다.
- **문제:** `--config`, `--scenario`, `--total-km` 등을 바꿔도 카드는 `config/default.yaml`, `100km`와 seed만 들어간 생성 명령을 표시한다. manifest에도 병합된 유효 설정과 전체 CLI 인자가 저장되지 않는다.
- **실제 재현:** 실제 `_card`에 `config/custom.yaml`, `scenario=['steam']`, `total_km=1`, `seed=7`을 전달했다. custom 설정 기록은 `False`, default 설정과 100km 표시는 `True`, 출력 명령은 `OMP_NUM_THREADS=1 python scripts/produce_data.py --seed 7`이었다. 이 재현은 카드 함수의 인자 보존을 확인한 것이며 custom 설정으로 전체 릴리스를 생성한 검증은 아니다.
- **최소 수정:** manifest에 원래 CLI 인자, 코드 커밋, 당시 병합된 유효 설정과 각 데이터 묶음의 실제 규모를 저장한다. 기본망과 별도로 적용되는 steam 설정도 구분한다. 카드는 저장한 값으로 작성한다. 원본 YAML의 경로만 보존하면 이후 파일 변경 시 복원이 불가능하므로 설정 내용도 보존한다.
- **미수정 영향:** 팀원이 카드의 명령을 따라도 다른 조건과 규모의 데이터를 만들 수 있다.
- **회귀 검증:** 기본값이 아닌 설정·시나리오·길이·표본 수로 카드와 manifest를 만들고 모든 값이 보존되는지 확인한다.

### 5. onboard 부모와 워커가 상대 경로를 다르게 해석한다

- **근거:** [maek/onboard.py](../../maek/onboard.py) 120~137행. 부모는 `Path(out_dir)`에 설정을 저장하지만 워커는 `cwd=root`로 실행한다. 기존 테스트는 절대경로 `tmp_path`를 사용한다.
- **문제:** 저장소 외부 작업 디렉터리에서 `PYTHONPATH`로 패키지를 찾고 상대 `--out data/eval`을 쓰면, 부모가 생성한 설정 경로와 워커가 읽는 경로가 다르다.
- **검증:** Windows의 `resource` import를 임시 대체한 뒤 실제 `run_all`과 설정 로더를 실행했다. 프로세스 실행 경계는 패치하여 부모와 워커가 해석하는 설정 파일 경로를 확인했다. 부모 설정 파일 존재는 `True`, 워커 기준 설정 파일 존재는 `False`였다. Windows의 1번 문제가 선행하므로 실제 워커 전체 실행까지 검증한 것은 아니다.
- **최소 수정:** 출력 경로를 부모에서 `Path(out_dir).resolve()`로 확정한 뒤 설정 파일의 절대경로를 전달한다.
- **미수정 영향:** 파일이 없으면 실패하고, 워커 위치에 이전 설정 파일이 있으면 잘못된 설정으로 측정할 가능성이 있다.
- **회귀 검증:** Linux 등 실행 가능한 환경에서 외부 CWD + 상대 출력 경로로 테스트하고, 과거 설정 파일이 있어도 현재 설정·seed·크기를 사용하는지 확인한다.

### 6. 두께 MAE가 성공 표본에만 조건부로 계산된다

- **근거:** [maek/evaluate.py](../../maek/evaluate.py) 180~195행.
- **문제:** NaN 두께 추정의 오차를 inf로 바꾼 다음 MAE에서는 유한값만 남긴다. 이름과 출력 표에는 성공한 추정만의 오차라는 사실과 실패율이 따로 표시되지 않는다.
- **실제 재현:** 정답 두께 `[10, 10]`, 추정 `[10.1, NaN]`인 통제 입력으로 실제 `eval_ut` 집계 함수를 실행했다. `thickness_mae_mm≈0.1`, 두 허용오차 내 비율은 모두 `0.5`였다.
- **최소 수정:** 현 값을 유효 추정에 대한 MAE로 명명하고 유효 개수·실패율을 함께 출력한다. 실패에 임의의 유한 오차를 대입할 필요는 없다.
- **미수정 영향:** MAE만 비교하면 추정 실패 증가를 놓칠 수 있다. 허용오차 내 비율에는 실패가 반영돼 있으므로 전체 평가가 실패를 모두 무시한다는 뜻은 아니다.
- **회귀 검증:** 정상·일부 실패·전부 실패 입력에서 MAE의 정의, 실패율, 표의 표시를 확인한다.

### 7. 전부 hit인 관측에서 a90의 상한을 단정한다

- **근거:** [maek/evaluate.py](../../maek/evaluate.py) 458~467행의 `pod_cell`, [docs/results.md](../results.md) 64·77·234행. a90은 검출 확률이 90%에 도달하는 결함 크기다.
- **문제:** `all_hit`이면 로지스틱 곡선의 a90을 식별하지 못했는데도 `a90 < 최소 시험 크기`로 표시한다. 관측 표본에서 모두 검출됐다는 사실과 검출 확률의 경계가 확인됐다는 주장을 구분하지 않는다.
- **실제 재현:** `pod_cell(pod_summary(np.arange(1, 11), np.ones(10)))`는 `전부 검출(a90 < 1.00)`을 반환한다. 검출 확률이 0.8인 모델에서도 10회 모두 hit인 사건의 확률은 `0.8**10≈0.1074`이므로 이 관측만으로 90% 성능을 확정할 수 없다.
- **최소 수정:** `전부 검출 — a90 추정 불가`로 표시한다. 상한을 주장하려면 시험 설계와 신뢰수준에 맞는 별도 추정 방법을 적용한다. Firth 등 별도 추정값이 있다면 그 값과 근거를 따로 표시한다.
- **미수정 영향:** 팀원이 결과 표를 성능 보증 경계로 과해석할 수 있다.
- **회귀 검증:** all-hit·all-miss·일반 적합 상태의 표시를 분리하고 결과 문서도 함께 갱신한다.

## 팀 작업 순서

1. **실행 담당:** Windows 지원 여부를 결정하고 1번을 해결한다. 그다음 5번을 수정해 외부 CWD에서 실제 워커를 검증한다.
2. **영상·평가 담당:** 2번의 결함별 정답 계약을 수정한다. 호출자와 테스트를 함께 바꾸고, 그 전후 POD·hit율 차이를 산출한다.
3. **데이터 담당:** 3·4번을 함께 처리한다. 새 출력 경로에서 작은 데이터셋을 만들고 manifest·파일 집합·재현 명령을 대조한다. 기존 공개 데이터는 자동으로 덮어쓰지 않는다.
4. **초음파·결과 문서 담당:** 6·7번을 고친 뒤 결과 표를 재생성한다. 지표 정의 변경과 수치 변경을 구분해 기록한다.

위 작업은 서로 다른 파일 또는 영역으로 나눌 수 있으나 `evaluate.py`를 수정하는 2·6·7번은 한 담당자가 통합하거나 수정 범위를 먼저 합의한다. 모두 합친 뒤 린트와 전체 테스트, 작은 규모 통합 생성을 다시 실행한다.
